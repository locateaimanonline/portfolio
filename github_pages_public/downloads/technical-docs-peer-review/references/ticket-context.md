# Issue context for a documentation review

If the request names an issue, use the available connection to read its summary, description, status, relevant comments, linked work, and acceptance criteria. Issue-key formats vary by organization; do not assume a particular project prefix. Comments may identify the branch, changed files, review stage, or unresolved SME question.

Compare the stated change with the user's explicit file targets and the actual diff. If they disagree, mention the mismatch and follow the user's requested review scope. Ask for the relevant issue text if no connection is available; do not invent it or silently treat the issue key as sufficient context.

Tie findings to the requested behaviour where useful, and distinguish a missing implementation from a documentation defect. Identify questions that require the author or subject matter expert. Prepare findings for the user; do not write to the issue unless the user requests that action.
